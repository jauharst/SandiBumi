#### MASK only blanks outputs; gr_normalize percentiles and log_predict training still consume flagged samples

- **Area:** prep/QC masking | **Effort:** medium | **Where:** src-tauri\src\workflow.rs:186

run_workflow_module_into (workflow.rs:181-207) runs the module on the full unmasked frame, then NaNs output samples where the MASK curve == 1 (199-205). The mask never reaches module inputs: ModuleContext (modules.rs:113-118) carries no mask, and workflow.rs:186 is the only MASK application site in the backend. Two Prep modules compute run-level statistics from their inputs before output masking happens: (1) gr_normalize (modules.rs:1512-1538) computes the well P_LOW/P_HIGH percentiles from every valid GR sample (1516, 1523-1524); its doc (1494-1499) says to 'mask the run to the reference interval to reproduce the field standard', which does not work — casing/washout/hot-streak GR still shifts P3/P97, and since those percentiles anchor the two-point transform, the mis-anchoring contaminates every output sample, flagged or not. Interval-restricted normalization (the field-standard P3/P97 method) is impossible via MASK. (2) log_predict's KNN training set (modules.rs:1595-1606) includes every sample where TARGET+predictors exist; its doc (1558-1559) says 'Mask the run to good-hole intervals so bad samples never train the model' — false as implemented: washed-out RHOB trains the model. Worse, OPT_COMBINE (incl. MAX_RAW) is applied inside the module (1677-1682) and the subsequent output masking blanks the result wherever mask==1, so the documented usage also deletes the repaired synthetic exactly in the washout intervals the MAX_RAW rule exists to fix. The badhole module doc (modules.rs:640-641) compounds this by promising the mask works for 'any module run'. Output masking hides contaminated samples but not their influence on run statistics — and for log_predict it removes the very output the module is for.

**Suggested fix:** Resolve the MASK curve BEFORE calling run_module and blank the module's input logs (or pass the mask into ModuleContext) so per-run statistics (percentiles, KNN training, facies training) only see unmasked samples; keep the existing output masking as well.

#### sw_height uses MD depth for height above FWL, no TVD option; SWH biased optimistic in deviated wells

- **Area:** saturation-height | **Effort:** medium | **Where:** src-tauri\src\satheight.rs:139

h = fwl - d at satheight.rs:139 uses ctx.log("DEPTH"), which the runner injects at workflow.rs:171 from the well's stored depth grid (fetch_curve_frame_from_set, equations.rs:482) — the LAS index, i.e. measured depth. DEPTH is not a selectable LogIn (spec at satheight.rs:101-118 exposes only PHIE/PERM) and there is no TVD input, so the module cannot consume the minimum-curvature TVD/TVDSS the codebase already computes (deviation.rs: minimum_curvature at :27, tvd_at at :81; stored per well in well_path, db.rs:1579), which is currently display-only (Phase 6c views per deviation.rs:78). The FWL param (satheight.rs:103) is bounded [0, 20000] m, so a subsea (negative TVDSS) FWL cannot even be entered — the user must supply an MD-reference value, and since dTVD/dMD = cos(inc) <= 1, MD-derived height overstates true height above the contact by ~1/cos(inc) (~15% at 30 deg, ~2x at 60 deg) over any deviated interval. Overstated h inflates Pc = 0.433*(RHO_W-RHO_HC)*h_ft and J; SWH_B is range-clamped to [-5, 0] (satheight.rs:108), so SWH = A*J^B is biased low — optimistic pay — in every legal configuration; the SKELT branch uses the same h and is equally affected, as is the HAFWL output (along-hole distance mislabeled as height, line 140). A second, opposite-signed artifact: the h <= 0 -> SWH = 1 cutoff (line 142) is also MD-based, so a horizontal/high-angle section held above the contact is flagged 100% water once its MD exceeds the entered FWL. Mahakam development wells are routinely deviated, so this is a first-order error for the primary user. Fix: optional TVD LogIn defaulting to DEPTH, or auto-resolve via tvd_at from well_path when a survey exists; document FWL as TVDSS (and widen its lower bound to allow negative subsea values).

**Suggested fix:** Add an optional log_in("TVD", ..., required=false) that defaults to DEPTH when absent (or auto-resolve TVD from well_path via tvd_at when a survey exists), and document FWL as TVDSS. Same consideration applies to the HAFWL output.

#### loadWell has no generation guard: fast well switching can render Well A's curves under Well B's title

- **Area:** race-condition / stale closure | **Effort:** small | **Where:** src\ui\logViewPanel.ts:438

loadWell (logViewPanel.ts:438-460) sets this.well and the panel title synchronously (440-441), then awaits getTrackData (444) and assigns this.series in the continuation — whichever in-flight response resolves last wins, regardless of which well it belongs to. Two subscriptions trigger it without serialization: selectedWell (246-250) and dataVersion (251-253); setLayout (435) is a third. The well_id check at 247 only dedupes same-well reloads and does not prevent the A→B race, since this.well is already B while A's fetch is pending. getTrackData is a raw Tauri invoke (ipc.ts:316-319); commands resolve out of order and DuckDB query time varies per well, so switch A→B quickly and B's title can sit over A's curve data — the stale continuation even fires setStatus("Loaded well A"). The catch path (448-451) is worse and deterministic: on failure this.series keeps the old well's data and refresh() is never called, so one failed fetch after a well switch leaves the previous well's log drawn under the new well's title — no race timing required. The same unguarded pattern lets a stale continuation overwrite coreByName (453-457) and revert topsEditor.setWell (459) to the previous well, so canvas, core overlay, and tops can end up showing three different wells' data under one title. For a petrophysics viewer, silently mis-attributed curves are the worst failure mode.

**Suggested fix:** Add a monotonically increasing request token: const gen = ++this.loadGeneration before the awaits; after each await, bail if gen !== this.loadGeneration. In the catch, clear this.series = [] and call this.refresh() so a failed load never leaves the prior well's curves on screen.

#### Long-running commands are sync Tauri v2 commands - a field-scale chain run blocks the IPC/main thread for minutes

- **Area:** backend/IPC threading | **Effort:** medium | **Where:** src-tauri\src\lib.rs:671

run_workflow_chain (lib.rs:670-690) executes chain::run_chain to completion (line 688) inside a non-async #[tauri::command]. In Tauri v2, non-async commands without the (async) attribute run inline on the main/event-loop thread; only async commands are dispatched to the async runtime. Grep confirms no command in src-tauri/src is async and nothing spawns threads except inversion.rs. The same applies to import_las_files (lib.rs:59), export_report_batch (:168), run_equation (:222), run_workflow_module (:440), run_monte_carlo (:454), run_ml (:461), and run_multimin (:468). Consequence at field scale: during a multi-minute 5-step chain across ~100 wells the host event loop is blocked, so every IPC invoke app-wide queues until the chain returns — the progress design is dead on arrival. workflowDialog.ts:473-483 deliberately fires runWorkflowChain un-awaited ("Fire the (blocking) run without awaiting") and polls getChainStatus every 250 ms (:484-494), but those polls and cancelWorkflowChain (:497-499, :516) are only serviced after the chain finishes: the progress bar sits at "Starting…" and Cancel is a no-op. (On Windows/WebView2 the webview itself renders out-of-process, so the page may still repaint — but all backend-dependent UI stalls and the native window goes "Not Responding" on drag/resize; practically a freeze.) The chain.rs module doc (line 12: "the run occupies its own command worker thread") and the lib.rs:668 command comment ("runs on its own worker thread") are both false — no thread is ever spawned. Ironically inversion.rs:49-64 (dispatch_inversion, a placeholder solver) already implements the correct pattern: tokio::spawn + spawn_blocking, immediate job-id return, registry poll — and its command comment (lib.rs:649-650) correctly notes the UI thread is never blocked. DbState is Mutex<Connection> (lib.rs:35), so moving work to spawn_blocking requires an Arc<Mutex<Connection>> (or equivalent) as the suggested fix states.

**Suggested fix:** Copy the dispatch_inversion pattern to every long-running command: change DbState to hold Arc<Mutex<Connection>>, make run_workflow_chain async (or return a job id immediately) and run chain::run_chain inside tauri::async_runtime::spawn_blocking. Same for run_workflow_module, run_equation, run_ml, run_multimin, run_monte_carlo, import_las_files, export_report_batch. This alone makes the existing 250 ms progress poll and cancel button actually work.

#### Rayon parallelism over wells is defeated: DB fetch and write both hold the single global Mutex<Connection>

- **Area:** backend/multi-well runs | **Effort:** large | **Where:** src-tauri\src\workflow.rs:146

run_workflow_module_into iterates wells with par_iter (workflow.rs:147), but each well's work is lock-bracketed on the single global Mutex<Connection> (lib.rs:35, the only production connection — db.rs:20, no try_clone anywhere): lock -> fetch_curve_frame_from_set + resolve_param_arrays (workflow.rs:153-168), unlock -> module math (microseconds for vectorized modules like vsh_gr/phi_dn/sw_indo on 10k samples), optional re-lock for MASK fetch (188-197), lock -> create_log_set + write_computed_curves_versioned with the guard held to closure end (workflow.rs:209-236). Since DB I/O dominates for these modules, the 'parallel' run serializes almost completely on the one mutex (compute-heavy paths like multimin or Python equations do still parallelize their unlocked math phase). The write path compounds it: write_computed_curves_versioned (equations.rs:435-470) issues a DELETE qualified by well_id + curve_name IN (...) — but computed_curves is deliberately PK-less and index-free (db.rs:106-122; the project measured the 3-column-PK ART index at 3.7x slower inserts, 311k vs 1.16M rows/s, and migrate_drop_computed_curves_pk rebuilds old DBs without it), so that DELETE is a sequential scan of a table that reaches ~50M rows at 100 wells x 50 curves x 10k samples — then appends every output row TWICE (current store + archive) via per-row appender.append_row with params! boxing. Per well-step that is ~60k-90k append calls (~55-80 ms at the project's own measured 1.16M rows/s) plus the DELETE scan that grows with table size: roughly 0.1-0.3 s serialized per well-step. A 5-step chain over 100 wells (chain.rs:143-171 runs steps sequentially, each over all wells) = 500 well-steps = roughly 1-2.5 minutes fully serialized under one lock (and, per the separate finding, while the UI is blocked). The project itself has measured this class of problem: montecarlo.rs:6-9 explicitly cites 'the single-writer DuckDB bottleneck measured for field-scale runs' as the reason MC avoids computed_curves writes entirely. run_equation (equations.rs:706-763) and run_python_equation (python_engine.rs:134-182) have the same lock-bracketed shape.

**Suggested fix:** Split read/compute/write phases per step: (1) do reads through per-thread connections (duckdb Connection::try_clone allows concurrent readers on one database) so fetch parallelizes; (2) keep one writer but batch a whole step: collect all wells' outputs, run a single transaction with one DELETE ... WHERE (well_id, curve_name) IN (...) covering the step, then one appender pass for all wells (and one for the archive). Expected: chain runs drop from minutes to tens of seconds.

#### The 'binary' curve transport actually ships every byte as a JSON number - ~4x raw size, parsed on the main thread

- **Area:** IPC payload encoding | **Effort:** medium | **Where:** src-tauri\src\equations.rs:60

TrackCurveSeries.data is Vec<u8> inside a plain serde-Serialize struct (equations.rs:56-61) returned from ordinary commands (get_track_data lib.rs:406, get_curve_data lib.rs:419, get_core_data lib.rs:119). No command uses tauri::ipc::Response and there is no serde_bytes or custom protocol (grep: zero matches), so Tauri v2 serializes the payload with serde_json and each byte becomes a JSON number — despite the struct's own comment claiming "bulk f32 arrays never cross the Tauri bridge as JSON". The frontend admits it: ipc.ts:287-296 handles data as "Uint8Array | number[] ... depending on the IPC transport". Cost: a byte averages ~3.5 chars as JSON, so packed f32 pairs cost ~14 chars per float — ~3.5x raw byte size and ~1.3-1.8x worse than plain JSON floats (not 2x; shortest-roundtrip f32 averages 8-12 chars). Note plain Vec<f32> JSON is not a safe alternative anyway: serde_json emits null for NaN, and fetch_curve_data pads gaps with f32::NAN (equations.rs:115) — the byte packing fixes NaN fidelity but not size/parse cost. Realistic numbers: get_curve_data for a crossplot (X/Y/Z + depth, 15k samples) = ~360KB raw -> ~1.3MB JSON parsed on the main thread per zone/curve change (crossplotPanel.ts:905; also histogramPanel.ts:498, pickettPanel.ts:174); get_track_data for a 50-curve layout min/max-decimated to a 400-1000px canvas = ~0.8-1MB raw -> ~3MB JSON, roughly 50-200ms of parse + number[]->Uint8Array conversion per well switch. This tax is also paid by EVERY open log panel on every dataVersion bump (logViewPanel.ts:251-252 -> loadWell -> getTrackData line 444 after each module run). unpackCurveSeries then copies twice more (alignment copy + two .slice(), ipc.ts:300-309), minor by comparison.

**Suggested fix:** Return real binary: one command variant returning tauri::ipc::Response whose body is a small header (JSON length-prefixed: curve names + point counts) followed by the raw f32 payload; on the JS side invoke receives an ArrayBuffer, so bytesToFloat32Array becomes a zero-copy Float32Array view (one aligned copy at most). Cuts well-switch payloads ~4x and eliminates the number[]->Uint8Array element-by-element conversion.

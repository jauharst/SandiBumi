# Guidebook prompt — the two-tier help system

Reusable brief for building and extending SandiBumi's user-facing help: the brief
in-app Help card (equation + published reference) and the complete offline HTML
guidebook, linked card → chapter. Authored 2026-08-25 from Jauhar's spec ("brief
explanation with equation and reference — paper or publication only — inside Help;
complete guide on HTML"). Run it as a normal increment session; it stops after the
first increment for a voice-and-mechanics check.

---

SandiBumi: build the two-tier help system — brief in-app Help, complete HTML guidebook.

GOAL
Pressing ? Help on a module gives a SHORT card: what the method is in two or three
sentences, THE EQUATION, and the published reference for it (paper or publication —
Archie 1942, not an internal doc), plus one link: "See complete guidebook", which opens
THAT module's full HTML chapter — screenshots, step by step — on an offline field
machine.

WHAT IS THERE NOW — build on it, do not duplicate it
- In-app help: workspace.ts openHelpForActivePanel() — PANEL_HELP one-paragraph blurbs
  per panel kind; a module pane currently shows its manifest's `doc` raw. The modal
  promises "Illustrated help for each panel will open here in a later release." This
  work fulfils that promise.
- docs/guide/first-hour.md — the narrative guide (voice already approved).
- docs/guide/reference/ — pages GENERATED from docs/generated/module_manifests.json
  (the committed dump of modules::list_modules(), drift-gated by
  manifest_reference_test.rs and check:module-reference). tools/gen-module-reference.mjs
  is the generator; hand-written prose folds in from reference/notes/<module>.md.
  THE MANIFESTS STAY THE SINGLE SOURCE OF TRUTH for every factual claim. The HTML
  guidebook is a further rendering of the same dump — never a hand-written copy of it.

VERSION 1 — in-app Help: brief, equation, publication
- Help stays a MODAL (the one standing exception to the working-pane rule), rendered
  from the ModuleSpec that already crosses the IPC.
- The card is exactly four things, in order:
  1. WHAT IT IS — two or three sentences. Derive from the manifest `doc`, trimmed to
     the method statement; the doc's implementation caveats belong to the guidebook,
     not the card.
  2. THE EQUATION — plain Unicode text the way the manifests already write it
     (SWT = (A·Rw/(PHIT^M·RT))^(1/N)). No LaTeX engine, no rendering dependency —
     the modal must work offline and load instantly.
  3. THE PUBLISHED REFERENCE(S) — paper or publication ONLY. Internal citations
     (docs/PRD_v2 sections, Geolog .lls line numbers, vendor helpfiles) are developer
     provenance and DO NOT appear on this card.
  4. The "See complete guidebook" link → this module's HTML chapter. A module whose
     chapter does not exist yet hides the link rather than 404ing.
- Non-module panels: keep PANEL_HELP blurbs, reviewed once against the house copy
  pattern; remove the "later release" promise line once the link exists.

PUBLICATION REFERENCES — the rule that makes or breaks this
- Publications live in ONE home in the code (a new manifest field on ModuleSpec, or a
  registry keyed by module id beside param_sources — implementer's choice, but a
  single home that reaches BOTH the help card and the HTML guidebook through the same
  dump, drift-gated like everything else).
- A citation is COPIED from where the repo already records it — docs/method_*.md,
  the PRD_v2 chapters, the manifests' own guidance/source strings, docs/IP_PROVENANCE.md
  — with author, year, and venue as recorded there. NEVER write a citation from
  memory: a plausible-but-wrong reference under an equation in a licensed product is
  the concealment failure the provenance rules exist to prevent.
- A module whose method has no publication recorded in the repo (in-house methods,
  utility modules like Splice or Clip) shows its named internal origin instead
  ("SandiBumi method — see docs/method_ssc_sspw.md" or simply no reference line for a
  pure utility), or the gap goes to Jauhar as a question. Utilities are not forced to
  cite a paper that does not exist.

VERSION 2 — the complete HTML guidebook
- One HTML chapter per module + an index, generated by extending the existing
  reference generator (or a sibling sharing its dump-reading code): the factual
  skeleton (doc, inputs, parameters with ALL their sources — internal provenance
  included here, this is where it belongs — options, outputs, pre-run checks) from
  module_manifests.json; the step-by-step walkthrough and screenshot sequence from a
  per-module authored content dir, kept strictly separate from generated output.
  Extend check:module-reference so stale/missing/orphaned HTML fails the gate exactly
  as the markdown does.
- Screenshots: the REAL app driven through the real flow, with the sandboxed method
  proven on the first-hour guide (isolated SANDIBUMI_CONFIG_DIR +
  WEBVIEW2_USER_DATA_FOLDER + sandbox cwd, WebView2 remote-debugging port, SANDI-*
  wells; never a real project; close by window-close, never a kill; free port 1420
  after). Numbers on camera follow the first-hour discipline: picked from the data,
  cited in the run's reference field, never presented as recommended values.
- Offline and self-contained: no CDN, fonts bundled the way the app bundles them or
  system fallbacks, images relative, one folder ships the whole book. Style follows
  the Organic tokens (docs/design_organic/); the brand terracotta is the brand's.
- English source; technical terms stay English; no client identifiers; SANDI-* only.

OPEN DECISIONS — put these to Jauhar before wiring, do not pick silently
1. Where the book ships: bundled into the installer as a Tauri resource (help works on
   a machine that never saw the repo) vs repo docs/ only. Bundled is the
   licensed-product answer but changes tauri.conf bundling.
2. How the link opens: OS default browser (shell.open — simplest) vs a dedicated
   in-app window (works on a field machine with no browser association).
3. Chapter scope for the first pass: all modules, or the first-hour path plus the
   Advance-tab methods fully authored, the rest skeleton-only until asked for.

HARD RULES
- Verify every claim about a control against the code or the running app;
  unverifiable claims become NAMED GAPS, never plausible sentences.
- Do not restate contracts that live in CLAUDE.md or docs/ — point at them. Anything
  generated gets a freshness gate wired into tools\check.ps1.
- Petrophysical parameters are cited from docs/ or a named source, or asked about —
  never invented; the same now applies to bibliography.
- Never force-kill npm run tauri dev. Stop the vite server when done.
- Where a chapter touches an optional-install capability (Python/numpy, scipy,
  dlisio, scikit-learn, Pillow, office packages), name it plainly with what happens
  without it.

DELIVER IN INCREMENTS, STOP AFTER THE FIRST
Increment 1: the wiring + ONE exemplar module end-to-end (suggest vsh_gr — its
first-hour chapter is raw material and its publications, Larionov/Stieber/Clavier,
are already named in the manifest's choice labels): the brief help card with equation
and publication, the full HTML chapter with screenshots, the working link between
them, and the extended gate. Stop and show it before the remaining chapters.
Increment 2+ (after "go ahead"): remaining chapters in batches, index, and the
non-module panel help review.

PROTOCOL
Normal increment protocol: verify (tsc + cargo test + a browser click-through of the
Help card and the link), REVIEW.md entry at the top, branch, commit, PR, report, stop

ADDENDUM — FIELD REVIEW RULINGS (2026-08-26, Jauhar)
The 52-chapter first pass shipped; these rulings govern the second pass and every
chapter written after it.

1. TWO READERS, ONE CHAPTER. Every chapter serves both a newcomer learning
   petrophysics from this book and a senior interpreter who expects the specific
   behaviour of every control to be stated. Concretely: the theory is taught, not
   assumed (what the measurement is, why the method exists), AND each parameter or
   option answers "what changes when I change this" (e.g. what happens when the KNN
   seed changes, what a different K does to the facies count) — not just what it is.
2. STRUCTURED, PROFESSIONAL VOICE. A consistent chapter skeleton in workflow order:
   what this is and when to reach for it → the physics → the picks and why → step by
   step → reading the result → QC and pitfalls → what the application enforces. No
   em-dash rhetoric (ruled 2026-08-26); plain professional prose.
3. DEDICATED STEP-BY-STEP SCREENSHOTS. One clean capture per step on an uncluttered
   workspace — the pane being taught beside the log/plot it drives, nothing else
   docked. Never a whole-workspace capture with unrelated module panes stacked in
   frame. Multiple screenshots per chapter, each beside the step it illustrates.
4. THE BOOK SHOWS NO INTERNAL PROVENANCE. Rendered pages carry no generator banner
   and no default_source strings (internal file paths, decision records) — those
   stay in the pane tooltips, the dump and docs/guide/reference/. Published
   references and DEC numbers quoted inside prose are fine.
5. NAVIGATION. Every page carries the left navigation pane (gen-guidebook.mjs
   navHtml) listing the whole book in workflow order with the current chapter
   highlighted, so a reader always sees where the module sits in the whole.
before merge. The gate is tools\check.ps1 green.

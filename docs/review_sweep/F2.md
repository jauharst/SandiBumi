## [High] `f64::clamp` panics on inverted bounds — zone parameters bypass the module dialog's range check

`F2a` · CODE-BUG · effort **M** · worth **fix-now** · verifier confidence high

**Where** `src-tauri/src/modules.rs:1818`

**Evidence**

```
// modules.rs:148-153 — the shared helper guards `v` but never `lo`/`hi`:
fn limit(v: f64, lo: f64, hi: f64) -> f64 {
    if v.is_nan() { v } else { v.clamp(lo, hi) }
}

// modules.rs:1813-1818 (sw_arch):
let swt_irr = ctx.p("SWT_IRR", i);
let swt_l = limit(swt, swt_irr, 1.0);

// workflow.rs:61-65 + 75-82 — no clamp to arg.min/arg.max anywhere:
let base = req_params.get(&arg.name).copied()
    .or_else(|| arg.default.parse().ok()).unwrap_or(f64::NAN);
...
if let Some(&(top, bottom)) = zone_range.get(zp.zone_name.as_str()) {
    for (i, d) in depth.iter().enumerate() {
        if *d >= top && *d < bottom { arr[i] = v as f64; }

// src/ui/zonesDialog.ts:177 — the value that lands in arr[i]:
const value = parseFloat(valueIn.value);
if (!zone || !param || Number.isNaN(value)) return;
await setZoneParam(well.well_id, zone, param, value, null);
```

**Failure** — `f64::clamp` is documented to panic if `min > max` or either is NaN. `src/ui/moduleDialog.ts:277` validates typed params against `arg.min`/`arg.max`, but the Zones dialog does not — its own hint text says "Any module parameter … Overrides beat the value typed in a module dialog", i.e. the zone override is designed to bypass that check. A petrophysicist entering irreducible water saturation in percent — zone `*`, param `SWT_IRR`, value `25` (spec range is 0.0–0.6 v/v) — then running SW-Archie hits `swt.clamp(25.0, 1.0)` → `assert!(min <= max)` fails → thread panic, run dies with the opaque `worker thread failed: task N panicked` from `jobs.rs:254`. The DB Inspector is a second unvalidated door: `dbInspectorPanel.ts:31` marks `zone_params.value_num` directly editable. The same shape is live at `modules.rs:1829` and `:1927`/`:2047` (`SWE_IRR`), `:500`/`:596` (`PHIE_MAX`, panics on a negative value), and `satheight.rs:189` `sw.clamp(swt_irr.max(0.0), 1.0)` — `.max(0.0)` neutralises NaN and negatives but not `SWT_IRR > 1`. Monte Carlo is a third door: `Distribution::Normal` sampling (`montecarlo.rs:55`) is unbounded by construction, so a normal distribution on any of these params draws out-of-range values by design. That this class is real is confirmed by the author's own guard at `shf_fit.rs:383`: "the Hd bounds below would invert (lo > hi panics f64::clamp)".

**Fix** — Clamp at the single choke point rather than at ~7 call sites: in `workflow::resolve_param_arrays` (and `montecarlo::resolve_zone_param`, which feeds `build_plans`), clamp every resolved value into `[arg.min, arg.max]` from the spec and map non-finite to the spec default, then note the coercion in the run result. Optionally harden `modules::limit` itself to `if !(lo <= hi) { return f64::NAN }` as a belt-and-braces guard for future modules.

**Verifier correction** — Claim stands as written; only a minor scoping refinement. The panic is contained by Tauri's spawn_blocking (jobs.rs:253-256 turns it into `worker thread failed: …`), so the failure is a dead module run with an opaque error rather than an app crash — severity is High for correctness/UX, not a process-kill. Also worth naming precisely: the root cause is the missing enforcement of the already-declared `ArgSpec.min`/`max` in `workflow::resolve_param_arrays` (workflow.rs:59-83), where zone_params overwrite the validated dialog value; `modules::limit` is merely where the assert fires.

**Priority rationale** — Fix now. This is a crash-to-desktop on ordinary user input, not a theoretical panic: `src-tauri/Cargo.toml:51-56` sets `panic = "abort"` on the release profile, so the `f64::clamp` assertion in `modules.rs:152` never reaches the `worker thread failed` handler at `jobs.rs:254` — the shipped app aborts the process with no dialog and no log line. The trigger is the single most common unit slip in this domain (entering irreducible water saturation as `25` instead of `0.25` for a param whose spec at `modules.rs:1751` is `0.0..0.6` v/v), on a control the app's own hint text advertises as the way to override module-dialog values. And it is persistent, not transient: `db.rs:2158-2178 set_zone_param` upserts the value into DuckDB with zero validation and `workflow.rs:61-84 resolve_param_arrays` never consults `arg.min`/`arg.max`, so the well stays permanently armed — every later SW-Archie run on it kills the app, with no diagnostic trail pointing back to the zone override the user set days earlier. A solo user would burn hours guessing at DuckDB corruption or a GPU fault. The fix is cheap and low-churn — `limit` is a 5-line helper and `resolve_param_arrays` a ~40-line single-purpose function, neither a large well-tested area. One amendment to the proposed fix: reject rather than silently clamp in `resolve_param_arrays`. Coercing 25 to 0.6 and returning a green "success" Sw curve would trade a visible crash for exactly the degraded-result-presented-as-clean-success violation that is this app's cardinal rule; the run should fail with `SWT_IRR = 25 outside spec range 0.0-0.6 (zone *)`, with `if !(lo <= hi) { return f64::NAN }` in `modules::limit` as the belt-and-braces guard for future modules.

## [High] NaN top depth from a tops CSV panics `partial_cmp().unwrap()` while the DB lock is held

`F2a` · CODE-BUG · effort **S** · worth **fix-now** · verifier confidence high

**Where** `src-tauri/src/tops.rs:320`

**Evidence**

```
// tops.rs:315-320, inside autocorrelate_multi
let mut markers: Vec<(String, f32)> = source_tops
    .iter()
    .filter(|t| want.as_ref().map_or(true, |w| w.contains(&t.top_name.to_uppercase())))
    .map(|t| (t.top_name.clone(), t.depth))
    .collect();
markers.sort_by(|a, b| a.1.partial_cmp(&b.1).unwrap());

// parsers.rs:1609-1612 — where the NaN gets in:
let depth = row
    .get(idx_depth)
    .map(|s| s.replace(',', "."))
    .and_then(|s| s.parse::<f32>().ok());
```

**Failure** — `f32::from_str` accepts `NaN`, `nan`, `NAN`, `+nan`, `inf`, `-inf` — a tops CSV/TXT with a literal `NaN` depth cell (what `pandas.to_csv(na_rep='NaN')` and `np.savetxt` emit for a missing marker) parses to `Ok(f32::NAN)`. `import_tops_file` (ingest.rs:515) writes it straight through `db::upsert_top`; nothing between the parser and the DB tests `is_finite()`. The user then runs Auto-correlate on that source well: `partial_cmp` returns `None` for the NaN pair, `.unwrap()` panics. Because `lib.rs:1337` holds `conn.lock().unwrap()` across the entire `autocorrelate_multi` call, the panic unwinds with the guard alive and poisons `DbState` — see finding #1. Note the neighbouring sorts in the same file (`median_step` at :424, `normalize_window` at :524) both pre-filter to finite values, so this one is an outlier, not a house style.

**Fix** — Two lines. In `parsers.rs:1612` add a finiteness gate: `.and_then(|s| s.parse::<f32>().ok()).filter(|d| d.is_finite())` — this also blocks `inf` depths from `1e40`-style cells. And change `tops.rs:320` to `.unwrap_or(std::cmp::Ordering::Equal)`, matching `shf_fit.rs:254` which already uses exactly that on the same NaN risk.

**Verifier correction** — Defect is real at src-tauri/src/tops.rs:320. Three mechanism corrections: (1) The panic does NOT crash the process — jobs.rs:244 runs the closure under tauri::async_runtime::spawn_blocking, so the unwind becomes a JoinError and the command returns Err("worker thread failed: ..."). The actual harm is exactly the secondary effect claimed: the std::sync::Mutex in DbState (lib.rs:55) is poisoned by the unwind while the guard from lib.rs:1337 is alive, so every subsequent conn.lock().unwrap() across the whole backend panics and the app is unusable until restart. (2) Precondition: sort_by only invokes the comparator when markers.len() >= 2, so a source well resolving to a single NaN-depth top does not panic at :320 (it panics later or produces garbage instead). (3) The reporter's claim that median_step (tops.rs:420) "pre-filters to finite" is imprecise — it filters `*s > 0.0`, which drops NaN incidentally but would still admit +inf. The proposed two-line fix (finiteness filter at parsers.rs:1612 plus unwrap_or(Ordering::Equal) at tops.rs:320) is correct and sufficient.

**Priority rationale** — Real, cheap, and the blast radius is far worse than "one command fails". I confirmed every leg: `parsers.rs:1609-1612` has no finiteness gate (`.and_then(|s| s.parse::<f32>().ok())` — `"NaN"` parses clean), `ingest.rs:515` writes it straight through `db::upsert_top` with no check, and `tops.rs:320` really is `partial_cmp(&b.1).unwrap()` while `lib.rs:1337` holds `conn.lock().unwrap()` for the whole call. The panic unwinds inside the job thread with the guard alive, poisoning the mutex — and `lib.rs` contains 89 `lock().unwrap()` sites, so from that moment every DB-touching command in the app panics too. One bad cell in one tops CSV bricks the entire backend until restart, taking unsaved session/layout state with it. The trigger is not exotic for this user: he routinely generates CSVs from Python tooling (chartdig, the mudlog digitizer), and `pandas.to_csv(na_rep='NaN')` / `np.savetxt` emit a literal `NaN` for a marker that was not picked in a well — exactly the shape of a multi-well tops export. Fix risk is nil: two isolated lines in code with no callers depending on the current behaviour (unparsable cells already `continue` at `parsers.rs:1614`, so gating non-finite depths matches the existing contract), and `shf_fit.rs:254` already sets the precedent with `partial_cmp(...).unwrap_or(std::cmp::Ordering::Equal)`, as do the finite-prefiltered sorts at `tops.rs:424` and `:524`. One caveat on sequencing: the parser-side `.filter(|d| d.is_finite())` is the load-bearing half. If you only swap the `unwrap()` for `Ordering::Equal`, a NaN depth sorts arbitrarily and `autocorrelate_multi` returns a nonsense marker order and warp *reported as a clean success* — which converts a loud crash into a silent wrong answer and trips this app's cardinal rule. Do both, parser gate first.

Load a saved Workflow-Builder chain containing gascorr with OPT_GATE=FLAGGED into the Monte Carlo dialog (monteCarloDialog.ts:177 reads chains straight from saved documents) for a well where condflag was never run. **Verifier correction** — The defect is real at the cited file:line with the cited mechanism, but "no indication at all / errors and notes both empty" is overstated. When the chain produces v/v PHI*/SW* outputs, the plausibility rollup sets checked=false with detail "no porosity/saturation samples to check" (montecarlo.rs:1541,1549) and monteCarloDialog.ts:1346-1347 renders it as a low-key bullet; with persist enabled, notes also gains "<well>: nothing to persist — no tracked output curve had finite values" (montecarlo.rs:1617). Also worth noting the trigger needs no explicit configuration — FLAGGED is the manifest default — and the same discarded-Err path affects the tornado sweep (line 950) and the all-median persist base run (line 1576), not only the main realization loop.

**Priority rationale** — This is a data-honesty failure of exactly the kind the app treats as cardinal, and it is reachable rather than theoretical. The `if let Ok(outputs) = modules::run_module(...)` at src-tauri\src-tauri\src\montecarlo.rs:1125 (verified in place, with the comment "A failed step just leaves the pool unchanged; downstream sees NaNs.") drops the one Err that survives build_plans' name validation — gascorr's guard at modules.rs:1470, whose own comment says it exists precisely so a FLAGGED run with an empty gas flag cannot "silently correct zero samples while reporting success". A gas-corrected chain with OPT_GATE=FLAGGED is a routine Mahakam workflow, and the Monte Carlo dialog replays saved chains against arbitrary wells, so hitting a well where condflag was never run is an ordinary user action, not a contrived one. The consequence is the worst kind: `pool.get("SWE").unwrap_or(&nanv)` at line 1293 yields all-NaN, zone_metrics returns NET/NTG/HPV = 0, and McResult comes back with `errors` and `notes` both empty — the user sees a P10=P50=P90 table of zeros that looks like a completed uncertainty run, and could carry those zeros into a volumetrics deliverable with no signal that the chain never executed. Small, localized, well-understood fix guarding against a silently wrong deliverable — no reason to defer it.

## Dimension summaries

### F2a — 6 raw

Of the 969 unwrap/expect matches, only 189 sit outside `#[cfg(test)]` modules, and 160 of those are `lock().unwrap()` on the shared `Mutex<Connection>` — leaving roughly 29 genuine value-unwraps on production paths. I traced every one of those 29. Most are correctly guarded and the code is unusually defensive about the classic LAS defect family: `parse_las_2` rejects truncated rows explicitly, `depth_keep_indices`/`sanitize_curve_columns` drop non-finite and duplicate depths (including the ±0.0 case), non-monotonic depth is warned not crashed, all-null-depth imports error instead of orphaning a well, `parse_core_csv` handles percent-vs-fraction, `montecarlo::build_plans` and `composite::render_pages` both bail on `depth.is_empty()`, `facies::prep_samples` forces k≥2 so the `% m` seeding can't divide by zero, and every `sort_by(partial_cmp().unwrap())` I checked in montecarlo/parsers/tops(median_step,normalize_window)/shf_fit(hs) pre-filters to `is_finite()`. I found no integer division or modulo by a computed zero anywhere on a production path — `montecarlo.rs:1356 iterations / batch` is guarded by `clamp(1, 100_000)`, and `composite::facies_color`'s `% n` uses a 12-element const. The real defects are elsewhere: three reachable panics (a NaN sort under the DB lock, `f64::clamp` with inverted bounds from unvalidated zone parameters, and a KNN sort poisoned by ±inf that the LAS importer lets through but the DLIS importer strips), plus a `.unwrap()`-on-poison policy across all 160 lock sites that turns any one of them into a permanent app brick, and an unguarded `.expect()` before the window is created.

### F2b — 6 raw

Two files are clean and two are not. workflow.rs (pay-summary / cutoff-sweep loops at 537, 552, 617, 785, 1021, 1050) and resultsqc.rs (compute_spread, 239 and 266) allocate nothing per sample — output buffers are hoisted, curves are borrowed slices, and the only per-method Vec in resultsqc is one alloc per Sw model per well. The problems are concentrated in three places. (1) The ModuleContext ABI itself: `p()` resolves a per-sample parameter through a `HashMap<String, Vec<f64>>` string lookup on every depth sample (95 call sites in modules.rs alone, plus 13 in ssc.rs and 9 in lrlc.rs), and `log()` returns an owned `Vec<f32>` clone. ssc.rs compounds this by writing its 23 outputs through `out.get_mut(k)` per sample, giving 36 SipHash string lookups per depth sample against roughly 80 ns of actual arithmetic. (2) montecarlo.rs `run_realization` deep-copies the entire curve pool, every zone-resolved parameter array, and the DEPTH curve for every module step of every realization — around 7.5 MB of memcpy and 250k+ Vec allocations per realization-set for a typical well, multiplied by the 5000-iteration runs this app is built for. (3) multimin2.rs rebuilds a `Vec<Vec<f64>>` design matrix per depth sample even though, on the no-FTEMP path, every row it pushes is a loop-invariant value already computed once before the well loop, and `solve_bounded_lsq` allocates a fresh workspace (~16 Vecs) on every active-set iteration of every sample. Net: roughly 80 heap allocations per depth sample in SandiMin and ~36 string hashes per depth sample in SSC, both on the corpus-scale path. None of the fixes require unsafe code or exotic techniques; the ssc.rs one is a ten-minute edit that just makes it match the sspw() function sitting 70 lines below it in the same file.

### F2c — 10 raw

The Result<T,String> boundary is largely correct: db.rs and parsers.rs carry typed thiserror enums (DbError/ParseError) internally, 55 of 56 db.rs signatures use DbResult, and String appears mostly at the #[tauri::command] edge or in genuinely user-facing validation paths (db::update_well_field, modules::run_module). ### F2d — 7 raw

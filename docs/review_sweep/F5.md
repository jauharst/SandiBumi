# F5 — Lifecycle & leaks review

**Run 2026-07-24** under `docs/engineering_review_prompt.md`. 5 dimensions (F5a dispose
symmetry, F5b listener accumulation, F5c well-group scoping, F5d subscription correctness,
F5e backend resource lifecycle), 51 agents, 0 errors. **23 raw findings → 20 survived → 3
refuted.**

## Method, and what these findings are NOT

Each dimension was reviewed by an agent that first restated the checklist as an expectation list,
then read the code. Every raw finding was then hit by **two independent agents**: one told to
adversarially REFUTE that the defect exists (defaulting to refuted when it could not positively
confirm), and a separate one judging whether it is worth a solo developer's time. Only findings
that survived refutation appear below; the 3 that did not are listed with the reason, because a
refuted finding is also a result.

**These are static findings — read from the code, verified by re-reading the code. None has been
reproduced by running the app.** Before fixing any of them, reproduce it first: several carry a
precise action sequence written for exactly that purpose. Treat the failure scenarios as
hypotheses with evidence, not as observed behaviour.

**F5a #1 and F5b #3 are the same defect**, found independently by two dimensions that were not
told about each other. That is corroboration, not two problems — count the actionable set as
**19**, not 20.

## Verdict

The frontend lifecycle discipline is genuinely good and the sweep says so: 21 of 23 dock
components are exactly dispose-symmetric, including the hard cases (`buildZoneSelect`,
`buildWellScope`, the `attachZoomPan`/`attachKeyboardPanZoom`/`attachResizeRedraw`/
`attachScatterTooltip` family — every caller honours every disposer). `LogCanvasRenderer` even
carries a comment warning about the exact window-listener trap that the two survivors fell into.
The leaks that exist are the "acquired in a nested closure, never released" shape, which is the
one the eye slides over.

**The backend is where the real problems are.** F5e produced 4 of the 7 High findings, and they
are not memory hygiene — they are correctness and honesty:

- **Cancel that does not cancel.** A Cancel button is rendered for every active job, but only 5
  of ~27 job kinds read the flag. The other 22 run to completion, **commit their writes**, and
  are then reported to the user as "Cancelled". This violates the project's cardinal rule that a
  degraded or failed result must never be presented as a clean one — here it is inverted: a
  *completed* run is presented as cancelled, after it has already written curves.
- **Project switch swaps the DuckDB connection under 8 in-flight commands**, which then finish
  against the wrong project.
- **A runaway Python script orphans a 100%-CPU `python.exe` that outlives the app**, with no
  timeout and no kill path.
- **A panic in the chain runner leaves both registries permanently "Running"**, refusing every
  project switch for the rest of the session.

And one flat user-facing bug worth calling out on its own: **the Report pane never opens** —
`buildWellScope`'s subscribe fires synchronously and reads `batchBtn` while it is still in the
temporal dead zone. That is the same failure mode as the V3 Vega TDZ crash, in a different place.

### F5a · Correlation panel leaks a window `pointerup` listener that pins every loaded well's curve data

- **Class** LEAK · **Severity** High · **Effort** S · **Scales** per-open-close-cycle · **Verifier confidence** high
- **Where** `src/ui/correlationPanel.ts:1040`

**Evidence**

```
Acquired at 1034-1040:
```ts
  let dragging = false;
  let lastY = 0;
  canvas.addEventListener("pointerdown", (e) => {
    dragging = true;
    lastY = e.clientY;
  });
  window.addEventListener("pointerup", () => (dragging = false));
```
The handler is anonymous — no reference is kept — and the returned cleanup at 1098-1105 releases only three of the four acquisitions:
```ts
  return {
    el,
    dispose: () => {
      resizeObserver.disconnect();
      unsubData();
      unsubTheme();
    },
  };
```
Contrast src/LogCanvasRenderer.ts:540-561, which handles the identical situation correctly and even documents the trap: "these live on `window` — which means they survive the canvas being removed on panel close. Keep named references and remove them in dispose(), or every closed log view leaks one pointerup + one pointermove that keep firing (and pin this renderer) for the app's life."

What the leaked closure pins: `dragging` is a `let` in the same function scope as `strips`, `canvas`, `el`, `contacts` and `wells`, so they share one closure context. `strips` is `WellStrip[]` (67-76) holding, per well, a `TrackCurveSeries` fetched at 1400 samples (463), a `TvdssMap` of two `Float64Array`s (62-65, 465) and the full tops list (470) — and `included` is seeded with EVERY well in the active group (127), so a correlation panel loads the whole group.
```

**Failure scenario** — Open a project with a 40-well active group. Ribbon/＋ menu → "New Correlation" (workspace.ts:1405 `openPlot` mints a fresh panel id every time, so this is a genuinely reopenable MULTI panel). Wait for the strips to load, close the tab, repeat 20 times over a working session. dockview disposes each panel and the cleanup runs, but 20 `pointerup` listeners remain on `window`, each rooting a full builder closure: ~34 kB/well (1400 samples × Float32 depth+value ×2 curves, plus the Float64 MD/TVDSS pair) ≈ 1.4 MB per cycle, ~28 MB retained after 20 cycles and never collectable. On a 200-well group it is ~7 MB per open/close cycle. Every pointerup in the app also dispatches to all N dead handlers. The user sees the Performance panel's MEM gauge climb monotonically across a session with no open panels to explain it, and the leak survives Reset Workspace and Open Session (both go through `dock.clear()` → the same dispose path).

**Fix** — Name the handler and remove it, exactly as LogCanvasRenderer does: `const onWindowPointerUp = () => { dragging = false; };` `window.addEventListener("pointerup", onWindowPointerUp);` then add `window.removeEventListener("pointerup", onWindowPointerUp);` to the dispose closure at 1100-1104. (Optionally also capture the `setTimeout(fit, 50)` at 1096 and `clearTimeout` it, so a panel closed within 50 ms doesn't run `fit`→`draw` on a detached canvas.)

**Verifier correction** — The finding stands as a real High leak, with two factual adjustments. (1) Retained size per well is UNDERSTATED, not overstated: 2 curves x 1400 samples x (Float32 depth + Float32 value) = 22.4 kB, PLUS the TvdssMap's two Float64Arrays (~22.4 kB) = ~45 kB/well, not ~34 kB — roughly 1.8 MB retained per open/close cycle on a 40-well group. (2) Growth class is precisely one leaked listener per correlation PANEL INSTANCE, not per rebuild: for kind === "correlation" the selectedWell subscriber (workspace.ts:1053-1056) only rebuilds when generation === 0, and dataVersion bumps route through the internal reload() (1076-1086) rather than a rebuild, so well-selection churn does not multiply the leak. It still grows unbounded per open/close cycle over a session. Everything else — location, quoted code, mechanism, reopenability, the LogCanvasRenderer contrast, and the secondary uncaptured `setTimeout(fit, 50)` at :1096 — checks out exactly as reported.

**Why this priority** — Fix it now, because this is the rare case where the defect is per-cycle-unbounded and the fix is a zero-risk three-line copy of a pattern that already exists in the same repo. I verified both sides: `src/ui/correlationPanel.ts:1040` really does register `window.addEventListener("pointerup", () => (dragging = false));` with no retained reference, and the `dispose()` at 1098-1105 releases only `resizeObserver`, `unsubData`, `unsubTheme` — so nothing can ever remove it. Correlation is genuinely multi-instance and reopenable (`src/ui/ribbon.ts:248` and `src/ui/workspace.ts:326` both route to `openPlot("correlation", …)`, which mints a fresh panel id per call), so the retained-closure count grows with open/close cycles, not with the handful of panel types — and because `dragging` shares a closure scope with `strips`, each dead listener pins that panel's whole `WellStrip[]`, i.e. per-well 1400-sample typed arrays for every well in the active group. On Jauhar's real data (40-200 well groups) that is roughly 1.4-7 MB pinned per cycle, monotonic for the process lifetime and surviving Reset Workspace / Open Session since both go through the same dispose path. That is exactly the "grows with every cycle and every well" category the bar reserves for real cost, not the "bounded by panel type, user restarts daily" category that would be close to free. Against that, the fix is `const onWindowPointerUp = …` plus one `removeEventListener` line in the existing dispose closure — it touches no rendering logic, changes no behaviour, and `src/LogCanvasRenderer.ts:540-561` already ships the identical named-handler-plus-cleanup shape with a comment spelling out this exact trap, so there is no design decision to make and nothing to churn. The fix is strictly less risky than the defect. I would fold in the `setTimeout(fit, 50)` at 1096 in the same edit (capture the handle, `clearTimeout` in dispose) since a panel closed inside 50 ms otherwise runs `fit`→`draw` against a detached canvas, but that is a rider, not the reason to schedule the work.

### F5b · Correlation panel leaks a window 'pointerup' listener that pins the whole panel (all wells' curve arrays + detached DOM) on every open/close

- **Class** LEAK · **Severity** High · **Effort** S · **Scales** per-open-close-cycle · **Verifier confidence** high
- **Where** `D:\XX. Arshilla\src\ui\correlationPanel.ts:1040`

**Evidence**

```
Line 1034-1040 registers an anonymous handler that dispose() cannot remove:

  let dragging = false;
  let lastY = 0;
  canvas.addEventListener("pointerdown", (e) => {
    dragging = true;
    lastY = e.clientY;
  });
  window.addEventListener("pointerup", () => (dragging = false));

The dispose at 1098-1105 does not touch it:

  return {
    el,
    dispose: () => {
      resizeObserver.disconnect();
      unsubData();
      unsubTheme();
    },
  };

Compare LogCanvasRenderer.ts:540-561, which solves exactly this and says so: "these live on `window` — which means they survive the canvas being removed on panel close. Keep named references and remove them in dispose(), or every closed log view leaks one pointerup + one pointermove that keep firing (and pin this renderer) for the app's life." crossplotPanel.ts:2047/2101 and vegaPanel.ts:733/757 also keep named refs and remove them; correlationPanel.ts:1040 is the only window-level listener in a panel builder with no removal.

What is pinned: `dragging` is a `let` in buildCorrelationContent's function scope, so the closure holds that scope's Context, which also holds `strips` (correlationPanel.ts:128 `let strips: WellStrip[] = []`), `el`, `canvas`, `wells`, `contacts` — every variable referenced by the sibling closures draw()/reload(). Each WellStrip (67-76) carries `series: TrackCurveSeries` (ipc.ts:409-413, two Float32Arrays), `tv: TvdssMap` (two Float64Arrays built at 96-109) and `tops: TopEntry[]`. reload() at 451-484 fetches these for EVERY included well, and `included` is seeded at line 127 with the entire (group-filtered) project: `const included = new Set(wells.map((w) => w.well_id));` at 1400 points per curve (getTrackData(..., 1400), line 463) that is ~11 KB of Float32 + ~22 KB of Float64 per well.

Correlation panels are never singletons — workspace.ts:1405-1418 openPlot uses `id: this.freshId(kind)` — so each open builds a brand-new closure, and createPlot's correlation branch (workspace.ts:1052-1056) rebuilds only at generation 0, so exactly one leaked closure per panel instance.
```

**Failure scenario** — With a 50-well group active: open a Correlation panel from the ribbon (Plot → New Correlation), let it load, close its tab, repeat 20 times. Each cycle strands one window 'pointerup' listener and permanently retains that build's `strips` array plus its detached `el`/`canvas` subtree, none of which are reachable from any UI element any more. After 20 cycles the tab bar is empty but ~34 MB of Float32/Float64 curve data and 20 detached panel DOM trees are still live (50 wells x ~34 KB x 20), and every mouse-button release anywhere in the app dispatches 20 dead handlers. On an ungrouped 2000-well project the same 20 cycles retain roughly 1.4 GB of decimated curve arrays and will OOM the WebView long before that; a single open/close already strands ~68 MB. Task Manager shows the process RSS climbing monotonically with no panels open — the exact symptom that has no other explanation because every other panel type releases cleanly.

**Fix** — Mirror LogCanvasRenderer.ts:544-561 — hoist the handler to a named const and remove it in dispose:

  const onWindowPointerUp = () => { dragging = false; };
  window.addEventListener("pointerup", onWindowPointerUp);

then in the dispose at 1100-1104 add `window.removeEventListener("pointerup", onWindowPointerUp);`. Also worth clearing `strips = []` and `contacts = []` in the same dispose so a stray reference elsewhere cannot hold the arrays.

**Verifier correction** — Finding stands as reported (LEAK, growth per open/close cycle AND per well — the compounding class, so High is justified). Two calibrations: (1) the CPU claim is negligible — N stranded `() => (dragging = false)` handlers per mouse release cost nothing; the entire cost is retention, so drop the "every mouse-button release dispatches dead handlers" framing. (2) The 1.4 GB / OOM figure assumes a 2000-well ungrouped project and is a hypothetical ceiling; the defensible, measurable number is ~34 KB x wells-in-active-group per open/close cycle (≈1.7 MB per cycle at 50 wells, ≈34 MB after 20 cycles with no panels open), retained for the app's life. The proposed fix is correct and matches the existing house pattern at LogCanvasRenderer.ts:544-561.

**Why this priority** — Verified real at D:\XX. Arshilla\src\ui\correlationPanel.ts:1040 (`window.addEventListener("pointerup", () => (dragging = false));`) against the dispose at 1098-1105, which only calls `resizeObserver.disconnect(); unsubData(); unsubTheme();` — the anonymous window handler is unremovable, and because it closes over `buildCorrelationContent`'s scope it pins `strips` (line 128) with every well's Float32/Float64 arrays from `getTrackData(..., 1400)` at line 463, plus the detached `el`/`canvas`. It grows per open/close cycle, not per panel type, and correlation panels are `freshId(kind)` so there is no singleton to save you. I would discount the report's headline numbers: with a realistic 40-60-well active group it is ~1.5-2 MB plus one dead handler per cycle, so the "Task Manager climbing" symptom needs a long session with heavy correlation churn before it is felt, and the 1.4 GB figure only applies to an ungrouped multi-thousand-well project. What makes it fix-now anyway is the cost side, not the severity side: the fix is three mechanical lines in one function (hoist to a named const, add one `removeEventListener` to the existing dispose), it changes no behaviour, touches no shared code, needs no test, and it is copy-paste of a pattern the codebase already applies in LogCanvasRenderer.ts:540-561, crossplotPanel.ts:2047/2101 and vegaPanel.ts:733/757 — correlationPanel is the lone deviation from a convention this project has already written a comment to justify. Deferring it costs more in re-reading the closure to re-establish what is pinned than doing it costs now, and leaving one outlier erodes the pattern that keeps every other panel clean.

### F5c · buildWellScope snapshots the well list and group membership once and never refreshes — every batch pane silently runs on a stale well set

- **Class** STALE-STATE · **Severity** High · **Effort** M · **Scales** per-run · **Verifier confidence** high
- **Where** `src/ui/wellScope.ts:40`

**Evidence**

```
L40-43 take a one-shot snapshot:
```ts
const wells: WellSummary[] = await listWells().catch(() => []);
const groups: WellGroupEntry[] = await listWellGroups().catch(() => []);
const wellById = new Map(wells.map((w) => [w.well_id, w] as const));
const allIds = wells.map((w) => w.well_id);
```
Every resolution path reads those snapshots: L176-177 `const g = groups.find((x) => x.group_id === groupId); return g ? g.well_ids.filter((id) => wellById.has(id)) : [];`, L184 `return allIds.filter((id) => customIds.has(id));`, L51-52 `const pins = () => appState.pinnedWellIds.get().filter((id) => wellById.has(id));`.
The only live subscriptions are L248-250:
```ts
unsub.push(appState.pinnedWellIds.subscribe(() => { if (mode === "pinned") emit(); }));
unsub.push(appState.multiSelectedWellIds.subscribe(() => { if (mode === "selection") emit(); }));
```
There is no `wellGroupsVersion` and no `dataVersion` subscription and no re-fetch, yet the comment above them (L246-247) claims "Live: pinning/selecting/**activating a group** while the dialog is open updates the count and, when relevant, the active scope." `moduleDialog.ts:261-262` repeats the same false claim: "the well scope tracks live state on its own, so nothing well-related to re-tick here." Meanwhile every scope-using pane is built by `workspace.ts:610-632 asyncPane`, which has no rebuild subscription at all (contrast `wellPane` L707 which rebuilds on dataVersion), so the snapshot lives as long as the pane stays open. `wellGroups.ts:41` bumps only `bumpWellGroupsVersion()`, which only objectTree (workspace.ts:935) and mapPanel listen to.
```

**Failure scenario** — (a) Membership edit: active group "Block A" = 12 wells. Open Cutoffs & Pay Summary — the scope reads "Group / Block A (12) / 12 wells". Go to Wells → Well Groups → Edit wells on Block A, tick 8 more, Save membership. The Wells pane now lists 20 and the status bar says 20. Return to the still-open pane and press Compute Summary: `resolveIds()` reads the stale `groups` array and sends the OLD 12 ids (summaryDialog.ts:62→71), so FLAG_SAND/RESERVOIR/PAY are versioned for 12 of 20 wells and the summary table is missing the 8 new ones. No error; the count chip and the dropdown label both still read "12" because they are computed from the same stale array. (b) Import: open a Module pane with scope "All" (30 wells), import 5 LAS wells from the ribbon — dataVersion bumps and the pane visibly refreshes its curve dropdowns (moduleDialog.ts:234-260) but `allIds` is untouched. Press Run: 30 of 35 wells are processed and the pane reports "All 30 well(s) computed" — a plausible success with 5 wells silently unprocessed. (c) ★ Pinned: pin a newly imported well while the pane is open; the pin subscription fires and updates the count, but `pins()` drops the id because `wellById` predates the import, so the count silently under-reports and the run skips it.

**Fix** — Make the scope re-resolve from live data instead of a construction-time snapshot: keep `wells`/`groups` in mutable locals, add a `refresh()` that re-runs `listWells()` + `listWellGroups()` (rebuilding `wellById`, `allIds`, the group `<select>` options, preserving `groupId` when it still exists), and subscribe it to both `appState.wellGroupsVersion` and `appState.dataVersion` (skipping the immediate first fire, the pattern used in workspace.ts:935 and moduleDialog.ts:254). Push both unsubscribes into the existing `unsub` array so `dispose()` still releases them. Also re-point `groupId` at `appState.activeWellGroup` when the active group changes, so a scope left on "Group" follows the workspace. Then delete the now-true-again comments at wellScope.ts:246-247 and moduleDialog.ts:261-262.

**Verifier correction** — The claim stands as written; two refinements. (1) Extra stale surface the reporter missed: `shownCustom()` at wellScope.ts:142-145 (`return q ? wells.filter(...) : wells;`) also reads the frozen `wells` array, so the Custom… checklist cannot even display a newly imported well — the fix must rebuild that list too, not just `allIds`/`groups`/the `<select>` options. (2) The staleness is not uniform across modes, which matters for triage: in "all", "group" and "custom" the id set is wholly frozen (the reporter's scenarios (a) and (b)); in "pinned" and "selection" the ids themselves come from live observables and only the `wellById.has(id)` membership gate is stale, so those modes under-report by exactly the wells imported since the pane opened (scenario (c)) rather than being wholly wrong. Growth class is not a leak — it is per-pane stale state: one frozen snapshot per open scope-using pane, wrong from the first well/group mutation onward and wrong on every subsequent run until the pane is closed and reopened. Severity High is right for the silent-wrong-result reason, not for accumulation. Also note the comment at wellScope.ts:246-247 over-claims on a third axis beyond the two the reporter named: there is no `activeWellGroup` subscription either, so "activating a group while the dialog is open" updates nothing, and the header doc at wellScope.ts:14-15 ("getWellIds() re-reads live state at call time") is true only of the pinned/selection observables, not of the well/group data they are filtered against — both comments need correcting alongside moduleDialog.ts:229-231 and :261-262.

**Why this priority** — This is a silent wrong-answer bug in a deliverable-producing path, and it fails in the exact direction that hides itself. Because the count chip, the group dropdown label, the hover tooltip and the run all read the same stale `wells`/`groups` arrays, a pane that is missing wells reports a self-consistent, plausible success ("All 30 well(s) computed") with no discrepancy the user could notice — the only signal is the Wells pane saying 35, in a different pane. The triggering sequence is not exotic: this app deliberately moved from modals to persistent dock panes, and "import a batch of LAS, then hit Run on the module/cutoff/summary pane I already had open" is the normal working rhythm for a multi-well study; `moduleDialog.ts:254` already refreshes its curve dropdowns on `dataVersion` while `moduleDialog.ts:261-262` explicitly declines to refresh the scope, so the pane visibly updates and thereby earns trust it hasn't got. Consequence is data integrity, not memory: FLAG_SAND/RESERVOIR/PAY get versioned for a subset, pay summaries and reports go out short of wells, and the shortfall surfaces days later when a well is missing from a table. Cost of the fix is small and contained — one file, mutable `wells`/`groups` locals plus a `refresh()` wired to `wellGroupsVersion` and `dataVersion` using the skip-first-fire pattern already established at `workspace.ts:935` and `moduleDialog.ts:254` — with no churn outside `wellScope.ts` and no API change for the 13 call sites, since they all go through `scope.getWellIds()`. The only real care needed is rebuilding the `<select>` options while preserving `groupId` and not clobbering `customIds`; that is far less risky than shipping runs on an unknown well set. Bonus maintenance value: the comments at `wellScope.ts:246-247` and `moduleDialog.ts:261-262` currently assert the opposite of the truth, so any future reader will re-derive the same wrong assumption until this is fixed.

### F5c · Correlation panel resolves the active group once and refreshes only on dataVersion, so a group switch leaves the whole multi-well view on the previous group

- **Class** STALE-STATE · **Severity** Med · **Effort** S · **Scales** per-open-close-cycle · **Verifier confidence** high
- **Where** `src/ui/correlationPanel.ts:123`

**Evidence**

```
The well set is filtered once at build (L123 `wells = filterByActiveGroup(await listWells());`) and the only refresh hook is dataVersion (L1076-1086):
```ts
const unsubData = appState.dataVersion.subscribe(() => {
  if (!dataPrimed) { dataPrimed = true; return; }
  // Refresh the well list first (imports/deletions/group change), THEN re-read curves —
  void refreshWells().then(() => reload()).then(draw);
});
```
The comment claims it covers "an import, delete, or **active-group change**", but `activateWellGroup()` (wellGroups.ts:38-44) calls only `setActiveWellGroup` → `syncWellGroups` → `bumpWellGroupsVersion()`; it never bumps `dataVersion`, and this panel has no `wellGroupsVersion` subscription. `refreshWells()` (L490-503) is therefore never invoked on a group change. The same stale `wells` array backs the Wells checkbox menu (L528), the field list (L666), and the contacts modal's Suggest well dropdown (L820).
```

**Failure scenario** — Open Correlation with group "Block A" active — 8 strips drawn, the button reads "Wells (8/12)…". Switch the active group to "Block B" from the Wells pane group bar: the Wells pane, object tree and map highlight all switch to Block B, but the correlation canvas keeps drawing Block A's strips and its Wells menu still offers only Block A's wells, with nothing on screen saying so. The user then picks tops and adds fluid contacts (the Suggest dropdown at L820 also lists only Block A) believing they are working the active group — edits land on wells that are no longer in scope. The stale view persists until the panel is closed and reopened.

**Fix** — Add a `wellGroupsVersion` subscription next to the existing `dataVersion` one (same primed-flag pattern) that calls `refreshWells().then(() => reload()).then(draw)`, and release it in the returned dispose alongside `unsubData`/`unsubTheme`. `refreshWells()` already does the right thing — it re-runs `filterByActiveGroup`, adds newly in-scope wells to `included` and drops the ones that left (L497-501); it just never gets called on a group change.

**Verifier correction** — The defect is real but the growth class, the quoted symptom and the consequence are wrong. (1) Growth class: NOT "scales per-open-close-cycle" — this is not a leak. It is bounded per-panel-instance staleness that self-heals: closing and reopening the panel rebuilds it with the current group (workspace.ts:1053 rebuild at generation 0), and any bumpDataVersion() — a tops edit (topsEditor.ts:203), curve edit, or module run — fires the L1076 handler which calls refreshWells() and silently corrects the list. Correct class: bounded, single-instance, self-correcting on the next data mutation or reopen. (2) The claimed button text "Wells (8/12)" does not occur: L519 is `Wells (${included.size}/${wells.length})…` and `wells` is already group-filtered, so it reads (8/8) — there is no denominator hint that anything is out of scope, which makes the symptom quieter than described. (3) The dominant symptom is the inverse of the one given: refreshWells() adds newly-in-scope wells to `included` (L499), so the loud failure after switching Block A -> Block B is that NONE of Block B's wells appear while the Wells pane, object tree and map all switched. ### F5a — 2 raw findings

Contract first: `DomPanel` (src/ui/workspace.ts:53-71) stores the closure returned by its `fill(host, params)` and calls it from `dispose()`. dockview-core really does call it on a single-panel close — `DockviewComponent._doRemovePanel` → `panel.dispose()` → `DockviewPanel.dispose()` (dockviewPanel.js:260-262) → `DockviewPanelModel.dispose()` → `content.dispose()`. `dock.clear()` (used by `resetWorkspace`/`applySession`) routes through `removeGroup` → the same `removePanel` path, so the closure also runs on Reset Workspace and Open Session. Conclusion: any acquisition not undone in that closure leaks for the life of the process, and every panel except the four anchors (`wellsTops`, `tops`, `processing`, `health`) can be closed and reopened.

I built the acquire/release ledger for all 50 files in src/ui (plus src/LogCanvasRenderer.ts, which log views own). The codebase is unusually disciplined here — 21 of 23 dock components are exactly symmetric, including the hard cases (`buildZoneSelect`'s `dispose` is honoured by all 5 callers; `buildWellScope`'s `dispose` by all 13 callers; `attachZoomPan`/`attachKeyboardPanZoom`/`attachResizeRedraw`/`attachScatterTooltip` disposers by every caller; `LogCanvasRenderer` even carries a comment warning about exactly the window-listener trap). 1. `correlationPanel.ts:1040` registers an anonymous `window` `pointerup` handler that the returned `dispose` never removes. Because it is a `window` listener it pins the whole builder closure — including `strips`, which holds a decimated 1400-sample curve series plus a Float64 MD→TVDSS map plus the tops list for EVERY well in the active group. Grows per open/close cycle AND with well count.

2. The Inspector's CodeMirror `EditorView` (`inspectorPanel.ts:202`) is destroyed on internal re-render (`inspectorPanel.ts:140`) but never on panel close: `InspectorPanel` has no `dispose()` at all, and `workspace.ts:989-992` only releases the two store subscriptions. Everything else in the sweep is clean; the coverage table records the full ledger so the negative results are auditable.

### F5b — 3 raw findings

The codebase is unusually disciplined about teardown — 30+ panel/dialog builders were checked and almost every one returns a dispose() that unsubscribes every appState.subscribe, disconnects every ResizeObserver, cancels every rAF/timer, and removes every window/document listener it added (LogCanvasRenderer even has a comment explaining exactly this hazard). One panel breaks the pattern and it is the worst possible one to break it in.

REAL FINDING: correlationPanel.ts registers an anonymous `window` "pointerup" handler at build time and never removes it. Because the arrow function closes over the builder's scope, V8 pins the entire panel Context — including `strips` (every included well's decimated Float32Array curve + Float64Array TVDSS map + tops) and the whole detached `el`/`canvas` DOM subtree. Correlation panels get a fresh dock id on every open (openPlot → freshId), so this grows one leaked listener + one fully-retained panel per open/close cycle, and the size of each retained panel scales with the well count (~34 KB/well of typed arrays; a 50-well group ≈ 1.7 MB per cycle, an ungrouped 2000-well project ≈ 68 MB per cycle). 20 cycles is the user-visible memory-growth case the review asked about.

SECOND (Low): the correlation panel's "Wells (N/M)…" dropdown is a copy of workspace.ts's `showAddPanelMenu` that drops its `document.querySelector(".dock-add-menu")?.remove()` guard, so clicking the button a second time stacks a duplicate menu instead of toggling it closed. It self-heals on the next outside mousedown, so it is a wrong-render bug rather than unbounded growth.

I could NOT find any duplicate-handler-on-refresh bug — the pattern the review flagged as highest value. Every re-render path I traced (inspectorPanel.renderGenericCatalog, objectTree.refresh, wellGroups.renderGroups/renderMembership/renderList, resultsQcPanel.compute, autoCorrDialog.renderProposals, viewerChrome.renderTrackHeaders, processingPanel.refresh, historyPanel.render, monteCarloDialog.renderResults) clears its host with innerHTML="" / textContent="" and rebuilds fresh elements, so listeners die with the nodes they were attached to. The handful of listeners bound to persistent elements (resultsQcPanel.ts:721 zoneSel, histogramPanel.ts:718, crossplotPanel.ts:1820, pickettPanel.ts:348) are all registered exactly once at build time. Panels that re-run a render on every click (hfuDialog, lorenzDialog, multiminDialog's recon QC) explicitly call `detachRender?.()` before replacing the DOM.

modal.ts and contextMenu.ts are both clean for this dimension: modal.ts closes the previous dialog via the module-level `activeClose` before opening a new one (so at most one keydown is ever live) and runs `dragCleanup` for an in-flight title-bar drag; contextMenu.ts defers its four document/window listeners by a task and tears them down from a MutationObserver on the menu's removal, with matching capture flags on the "scroll" pair. The only way to strand contextMenu's listeners is two synchronous showContextMenu calls in one task, and there is exactly one call site (workspace.ts:757, on a per-panel element, never nested), so it is not reachable.

No module-level cache keyed by well id or curve name exists anywhere in src/ — i18n.ts uses WeakMaps, undo.ts caps at LIMIT=100, processLog.ts caps at LIMIT=5000, dirty.ts entries are cleared in the log view's dispose. No setInterval is left running (healthPanel 1500 ms, processingPanel 500 ms, workflowDialog 250 ms all clear in dispose).

### F5d — 7 raw findings

STORE SEMANTICS (src/state.ts:27-31): `subscribe(fn)` adds the listener to a `Set` and then calls `fn(this.value)` SYNCHRONOUSLY before returning the unsubscribe closure. `set(v)` assigns then iterates the Set synchronously. So every subscription is also an immediate synchronous invocation, in the caller's own stack frame — and if the caller is an `async` function suspended at an `await`, that invocation runs while the rest of the caller's `const`/`let` bindings are still in the temporal dead zone. That is exactly the hazard the codebase has already been bitten by (see the defensive comment at vegaPanel.ts:393-395, and the `dataPrimed`/`firstData`/`firstGroups`/`first` guards in crossplot, histogram, pickett, correlation, map, unconventional, moduleDialog, plotCommon and workspace).

The immediate-fire discipline is good almost everywhere. The re-fetch-vs-repaint split is CLEAN: I found zero themeVersion handlers that re-fetch (logViewPanel.ts:328-337 and vegaPanel.ts:565-571 both carry comments showing a re-fetching version was deliberately removed; vega's `repaint()` re-embeds cached `lastRows`), and zero dataVersion handlers that repaint from cache instead of re-fetching. Generation counters are present on 13 of 18 subscription-driven async reloads.

What is broken: (1) one live TDZ crash — the Report pane fails to open outright whenever the well scope resolves to "pinned" or "selection", because buildWellScope's immediate subscribe fire reaches back into a `const` the caller has not reached yet; (2) three unguarded reloads that are each driven by TWO immediate-firing subscriptions (DB Inspector, Tops, Curve Catalog), the worst of which turns a lost race into a wrong-row database WRITE; (3) the Vega panel is the only curve-data plot with no dataVersion subscription at all; (4) six Canvas-2D dock panes read the palette at draw time but never subscribe themeVersion, and `attachResizeRedraw` explicitly ignores same-size events, so their canvases keep the old palette permanently.

### F5e — 7 raw findings

Seven findings. The headline is the project-switch case the brief asked me to check explicitly, and it IS broken — but not via a cache. There is no per-well/per-project cache in the Rust backend at all (only four managed states: DbState, ProjectState, ChainRegistry, JobRegistry; the only global statics are the Python path OnceLock and a CPU-tick baseline), so cached-state-survives-switch is genuinely clean. The hole is the guard itself: `open_project`/`new_project` gate on `chain::any_active || jobs::any_active`, and eight commands run off-thread with an `Arc<Mutex<Connection>>` clone WITHOUT registering a job, so `project::switch_project` swaps the Connection *inside* the mutex underneath them and they finish reading a different project's database. The second-highest is the Python worker: `exec` blocks on `read_exact` with no timeout and no kill path, the cancel flag is only read between wells, and a runaway user script leaves an orphan `python.exe` at 100% CPU that survives closing SandiBumi, plus a job that never reaches a terminal phase (so it is exempt from `prune` AND keeps `any_active` true, blocking project switching for the session). Third, Cancel is rendered for every active job but only 5 of ~27 job kinds ever read the flag — the other 22 run to completion, commit their writes, and are then finalized as "Cancelled". Temp files are clean (production export/import paths write straight to the user-chosen destination; every `env::temp_dir()` hit is in `#[cfg(test)]`), and DuckDB transactions/appenders/statements are clean: `with_txn` rolls back on Err, the two hand-rolled BEGIN blocks in `ingest.rs` ROLLBACK on every early return, appenders are always dropped before ROLLBACK, and there is no nested `with_txn`.

- **dbInspectorPanel.reload has no race guard; a stale page can be edited against the newly-selected well** (`src/ui/dbInspectorPanel.ts`) — The quoted code is accurate (no gen token in reload(), five unserialised triggers, commitEdit reads live selectedWell against a closed-over stale row), but the claimed failure mechanism is inverted and therefore unreachable. reload()'s only await is getTablePage -> invoke("get_table_page"), and that command is a SYNCHRONOUS #[tauri::command] fn whose first line is `let conn = db.0.lock().unwrap();` against the single global `DbState(pub Arc<Mutex<Connection>>)` (src-tauri/src/lib.rs:55, 1188-1198), with both the COUNT(*) and the page SELECT executed inside that one lock hold (src-tauri/src/db.rs:1233-1257). In the reporter's own scenario, request A acquires the connection mutex hundreds of ms before the user can click well B and holds it for its full ~1 s, so B cannot start until A returns. Responses and promise resolutions are therefore in issue order and `this.page` always converges to the LAST-issued well. The stated end state ("reload(B) ... finishes first; reload(A) then resolves and overwrites this.page") is the reverse of what the serialisation produces, so the persistent A-rows-under-B-header render and the resulting updateStandardSample(B, A_depth, ...) wrong-well write do not occur. A residual transient does exist (scopeEl is set synchronously at line 120 before the await, so A's rows are briefly painted under "Well: B" while B's fetch is outstanding), but any open edit input is destroyed by `this.gridHost.innerHTML = ""` at line 177 when B lands, and Chromium does not fire blur on removal of a focused node, so finish() never runs and no commit is issued. Hitting the wrong-well write requires a double-click plus Enter inside a sub-second refresh window. The gen-token pattern cited in crossplotPanel.ts:1478 / histogramPanel.ts:567 / pickettPanel.ts:315 / correlationPanel.ts:450 is consistency, not proof of a defect here — those panels sit behind the same global mutex.

### F1e — 9 raw

The dominant convention in this frontend is good and is followed almost everywhere: user-triggered runs use `btn.disabled = true` → `try` → `catch (e) { statusLine.textContent = \`Failed: ${e}\` }` → `finally { btn.disabled = false }`, surfacing the raw backend string (hfuDialog, thomeerDialog, lorenzDialog, faciesTieDialog, summaryDialog, shfDialog, mlDialog, moduleDialog, monteCarloDialog, multiminDialog, cutoffDialog, dashboardPanel, reportDialog, compositeDialog are all textbook). I found no dialog where a Run button is left permanently disabled on an error path, and the canvas plot panels (crossplot, histogram, pickett, unconventional, vega, correlation, logView) are the best-guarded code in the repo — they bail on BOTH the success and error branches of the generation check so a superseded error can't clobber newer data. The gaps cluster in two places. First, the **write/undo layer**: `src/undo.ts` awaits `action.undo()` with no try/catch and both call sites use `void undo().then(...)` with no `.catch`, so a rejected undo silently deletes the action from both stacks and still tells the user it worked; `ribbon.ts` makes it worse for core-shift by discarding the promise entirely with `void`. Doing async reloads WITHOUT one: **dbInspectorPanel.reload** (5 trigger sources, and the stale page is editable — reported), **inspectorPanel.refreshCatalog** (dataVersion + selectedWell + tab click + 4 buttons — reported), **topsPanel.refresh** (selectedWell + dataVersion — reported), plus three lower-risk ones I did not report separately because no wrong render follows: `mapPanel.loadWells` (dataVersion only, worst case one-version-stale markers), `topsEditor.setWell` / `highlightsOverlay.setWell` (only called from the already-gen-guarded `logViewPanel.loadWell`), and the `healthPanel`/`processingPanel` interval pollers (idempotent full redraws).

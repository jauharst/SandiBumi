## P0 — The Field Dashboard exports foot-project hydrocarbon pore thickness under a metre header, inflating the delivered value by 3.28084×.

**Decisive code.** `src-tauri/src/workflow.rs:4555-4564` constructs sample thickness from unconverted adjacent project depths, and `src-tauri/src/workflow.rs:4684-4759` accumulates `net` and `hpv` from that raw thickness. That is internally consistent if the result remains in the project's declared depth unit. The frontend breaks that contract: `src/ui/dashboardPanel.ts:17-48` hard-codes `HPV (m)` and `Net (m)`, `src/ui/dashboardPanel.ts:205-233` hard-codes `m` on the KPI cards, and `src/ui/dashboardPanel.ts:535-552` writes those static labels and the raw backend values straight to `field-dashboard-*.csv`. This panel neither obtains the project's depth unit nor converts the values.

**Concrete failure scenario.** Use a foot-declared project with a fully sampled 1,000–1,100 ft zone. Let every sample pass PAY, with PHIE = 0.20 v/v and SWE = 0.25 v/v. The backend correctly accumulates 100 in project-depth units for net and `0.20 × (1 - 0.25) × 100 = 15` for HPV. The dashboard presents the net KPI as `100.0 m` and the CSV places `15` under `HPV (m)`. The physical metric values are 30.48 m net and 4.572 m HPV. A CSV handed to a client therefore contains a plausible number with an explicit unit that is wrong by exactly 3.28084×.

**Self-refutation attempt.** I checked whether the backend canonicalizes pay thickness to metres, whether the dashboard obtains a project-unit preference, and whether export performs a late conversion. None does. As a control, the Office export path in `src-tauri/src/office.rs:474-495` and `src-tauri/src/office.rs:798-837` explicitly resolves the project depth unit and builds unit-aware sheet labels, showing that project depths are not globally canonical metres. That separate path does not save the dashboard's client-side CSV.

**Severity: P0.** This is a normal export path that can put an explicitly mis-unitized petrophysical quantity into a client deliverable.

## P1 — RtC converts a missing CAPBW sample to zero and emits a plausible clean-sand Sw instead of a missing result.

**Decisive code.** In `src-tauri/src/lrlc.rs:147-207`, `prefer` first preserves a sample as NaN when neither `CAPBW` nor `CAPBW_SSPW` is available, but line 173 immediately converts that NaN to `0.0`. The resulting excess conductivity is then clamped and a finite `RT_CORR` and `SWT` are written. `ModuleContext::log` in `src-tauri/src/modules.rs:1173-1175` establishes NaN as the missing curve/sample representation; there is no accompanying bit that distinguishes “the optional role was deliberately absent for this run” from “the selected capillary-bound-water curve has a hole at this depth.”

**Concrete failure scenario.** At one depth use RT = 20 ohm·m, PHIT = 0.25, RW = 0.30 ohm·m, M = N = 2, QV = 0.30, A_CAP = 0.45, B_QV = 0.0057, C0 = -0.0071, and RSF = 2.25. With a valid CAPBW = 0.08, the implemented equation gives applied excess conductivity 0.017218125 mho/m, `RT_CORR = 30.50466 ohm·m`, and `SWT = 0.396677`. If that one CAPBW sample is NaN, the code substitutes zero; the excess term becomes negative and is clamped to zero, so `RT_CORR = 20` and `SWT = 0.489898`. The missing input has therefore become a finite saturation 0.09322 v/v higher, with no gap or warning on the output curve.

**Self-refutation attempt.** I checked the intended optional-input behavior and the tests. A wholly absent capillary correction is intentionally allowed to collapse to the base resistivity model, and the IMTS test at `src-tauri/src/lrlc.rs:1719-1732` similarly pins the no-clay role to an Archie-like result. That does not rescue a *sample-level* hole in a curve the user did select: zero CAPBW is a valid geological statement, whereas NaN is the project's only missing-value statement. The `prefer` test at `src-tauri/src/lrlc.rs:1606-1611` even asserts that neither source available stays missing; the unconditional zero substitution after `prefer` defeats that assertion at the module output. I found no caller-side mask or prevalidation that restores the gap.

**Severity: P1.** The wrong finite Sw is reachable in ordinary processing of a partially missing bound-water curve and is visually indistinguishable from a valid answer.

## P1 — SSPW still uses the superseded 1.6-weighted gas pull even though the module declares the RMS midpoint used by SSC.

**Decisive code.** The custody statement at `src-tauri/src/ssc.rs:20-22` says gas conditioning uses the RMS midpoint from the cited `sspw.lls` branch and identifies the earlier 1.6 form as an overshoot. SSC implements that midpoint at `src-tauri/src/ssc.rs:182-203` as `sqrt((PHIDI² + NPHI²) / 2)`. The SSPW block at `src-tauri/src/ssc.rs:488-502` says “Same gas conditioning as SSC” and records the same branch identity, but actually computes `sqrt(PHIDI² - 1.6 × |PHIDI² - NPHI²| / 2)`.

**Concrete failure scenario.** Use RHOB = 2.32 g/cc, NPHI = 0.05 v/v, VSH = 0.20, RHOB_MAT = 2.65 g/cc, RHOB_FL = 1.00 g/cc, and RHOB_DSH = 2.71 g/cc, with all other SSPW inputs valid. `PHIDI = 0.20`, so the gas branch runs. The surviving 1.6 expression gives corrected density porosity 0.10, RHOB_COR = 2.485 g/cc, dry-mix RHOMA = 2.662 g/cc, and PHIT = 0.106498. The declared RMS midpoint gives corrected density porosity 0.145774, RHOB_COR = 2.409473 g/cc, and PHIT = 0.151941. SSPW therefore understates total porosity by 0.045443 v/v for this ordinary density-neutron crossover.

**Self-refutation attempt.** I checked `docs/method_ssc_sspw.md:15-17`; it still transcribes the older 1.6 SSC form, while the current Rust custody header explicitly says that form was superseded after checking the cited branch. Even setting that documentation drift aside, the defect survives as an internal contradiction: the SSPW site claims the *same* conditioning and the *same* custody identity as SSC but executes a different equation. The branch tests at `src-tauri/src/ssc.rs:776-843` count branch labels; they do not assert the SSPW corrected porosity or equality with SSC. The method note also says SSPW remains pending reference-suite validation, so there is no external result pinning the surviving equation as intentional.

**Severity: P1.** A normal gas-crossover sample produces a materially wrong finite porosity that feeds all downstream saturation and pay calculations.

## P1 — The saturation-height dialog labels FWL in metres while the backend requires FWL in the project's raw depth unit.

**Decisive code.** `src-tauri/src/satheight.rs:113` declares the FWL parameter unit as the literal `m`, and `src/ui/moduleDialog.ts:430-439` displays that literal without project-unit substitution. The calculation at `src-tauri/src/satheight.rs:171-200` first subtracts FWL directly from raw TVD/DEPTH and only then converts the resulting height through `ctx.depth_unit`. The runtime contract at `src-tauri/src/modules.rs:1109-1115` is explicit that DEPTH and any depth-derived parameter such as FWL are in the project's declared depth unit. Other module parameters use the special `depth` unit token when their display unit must follow the project; FWL does not.

**Concrete failure scenario.** In a foot-declared project, take a vertical-depth sample at 6,500 ft and a true FWL at 6,565.62 ft, giving 65.62 ft = 20 m height above FWL. Select SKELT with SH_A = 0.8, SH_B = 20 m, SH_C = 1, SH_D = 0, and a nonbinding SWT_IRR. Because the field is labelled metres, a careful user enters the physically equivalent FWL value 2,001.2. The backend evaluates `h = 2001.2 - 6500`, concludes the sample is below FWL, and returns SWT = 1.0. Supplying the undocumented raw-foot value 6,565.62 instead produces the intended 20 m height and `SWT = 1 - 0.8 × exp(-1) = 0.705696`.

**Self-refutation attempt.** I checked for a frontend conversion and for a backend convention that all parameters are SI. Neither exists. The feet-equivalence test at `src-tauri/src/satheight.rs:387-423` actually confirms the hidden input contract: it supplies FWL = 6,561.6798 when the project is in feet and obtains the same answer as FWL = 2,000 in a metric project. That test proves the physics conversion works *after* subtraction, but it does not convert the user's metre-labelled entry. I found no special-case transformation in the generic module dialog or workflow parameter resolver.

**Severity: P1.** A foot-project user following the displayed unit gets an ordinary, finite, and potentially fully-water-saturated answer from the wrong height.

## P1 — Curve and core depth-edit controls label values as metres but apply them directly as raw project-depth units.

**Decisive code.** The manual curve editor labels Shift, Top, and Bottom as metres in `src/ui/curveEditDialog.ts:38-55` and sends those numbers unchanged at `src/ui/curveEditDialog.ts:130-139`; `src-tauri/src/curve_edit.rs:773-839` compares and interpolates them directly against the stored depth grid. The core registration dialog likewise labels and records the shift as metres in `src/ui/ribbon.ts:1484-1537`, while `src-tauri/src/db.rs:9228-9249` performs `depth = depth + delta` on the active core delivery. Neither path reads the project depth unit or calls the depth conversion helpers.

**Concrete failure scenario.** Open a foot-declared well and enter a +3.0 shift because both dialogs explicitly say metres. The curve path resamples at `d - 3.0` on a foot grid, and the core path adds 3.0 to foot-valued plug depths. Both move the data by 3 ft = 0.9144 m, leaving a 2.0856 m registration error. The curve interval operations have the same problem: a “Top 3,000 m / Bottom 3,010 m” edit is matched against raw foot depths, so it edits the wrong interval or nothing at all.

**Self-refutation attempt.** I checked whether the application globally stores metres regardless of the imported project unit and whether a shared display preference converts these fields. It does not: `src/depthUnitPref.ts:24-56` carries an explicit project/display unit state, while these dialogs do not import or use it. The renderers consume the stored project-unit grid, and the backends receive only untyped floats. Both operations are undoable, which limits recoverability risk, but undo does not make the initially applied registration correct or warn the user that the unit label was false.

**Severity: P1.** These are normal interactive QC/registration operations whose wrong but plausible alignment can alter every subsequent curve/core comparison.

## P1 — Contact suggestion and the correlation-pane consistency check use metre-scale constants on raw project depths, causing false flags and scale-dependent picks in foot projects.

**Decisive code.** `src-tauri/src/contacts.rs:54-143` describes and applies ±5 m contrast windows, a 2 m duplicate cluster, and a resistivity window supplied as 3.0, but all comparisons operate directly on fetched project depths. `src-tauri/src/contacts.rs:442-480` documents `flag_abs` as metres and compares it directly with raw TVDSS residuals. The Tauri wrapper defaults that threshold to 3.0 at `src-tauri/src/lib.rs:3832-3849`. The correlation pane calls it without an override and labels RMS as metres in `src/ui/correlationPanel.ts:1368-1401`. None of these paths reads or converts the project's depth unit.

**Concrete failure scenario.** In a foot-declared project, store two well-scoped TVDSS contacts at 1,000 ft and 1,010 ft with no surface coordinates, so the flat mean is 1,005 ft and each residual is exactly 5 ft. A true 3 m flag threshold is 9.8425 ft, so neither well should be flagged. The correlation-pane path compares `5 > 3`, flags both wells, and reports RMS `5.0 m` even though the value is 5 ft (1.524 m). On the suggestion path, the nominal 5 m Sw-contrast window is only 5 ft and the nominal 3 m resistivity window is only 3 ft, changing which crossover/drop wins and its confidence.

**Self-refutation attempt.** I used already-TVDSS contacts in the scenario, so MD-to-TVDSS survey conversion cannot explain the discrepancy. I also checked the newer Fluid Contacts pane: `src/ui/fluidContactsPanel.ts:315-349` correctly calls its editable tolerance “Depth units” and passes it explicitly. That local wording makes that pane internally coherent, but it does not save the correlation-pane default/`m` label, nor the suggestion algorithms whose constants are still described as metres. Tests at `src-tauri/src/contacts.rs:1237-1297` use unitless metre-like fixtures and do not repeat the cases in feet.

**Severity: P1.** Normal use in a foot project produces wrong QC flags, wrong displayed residual units, and potentially different suggested contact depths.

## P1 — Two core-to-log readers omit the declared-datum guard and numerically pair TVD/TVDSS core plugs with MD logs.

**Decisive code.** Core import stores the delivered numeric depth and its declared datum without transforming it (`src-tauri/src/ingest.rs:1743-1788`). `src-tauri/src/db.rs:4097-4150` therefore provides a guard that refuses depth pairing unless the active core delivery is MD; sibling readers such as `get_scal_pc` and `get_core_point_series` call it. `get_core_plugs` at `src-tauri/src/db.rs:4184-4199` and `get_core_por_gd` at `src-tauri/src/db.rs:4242-4256` do not. Their callers then do raw numeric nearest-depth matching: `src-tauri/src/facies_tie.rs:282-357` for core facies/permeability ties and `src-tauri/src/sandimin.rs:1979-2030` (through the core-fit path at `src-tauri/src/sandimin.rs:1301-1343`) for porosity/permeability fitting.

**Concrete failure scenario.** In a deviated well, let the log contain MD 1,000 with class 1 and MD 1,200 with class 2. Import an active core delivery declared TVD whose plug at TVD 1,000 physically corresponds to MD 1,200, with permeability 100 mD. The import stores depth 1,000 plus the TVD declaration. `get_core_plugs` returns the raw 1,000; facies tie's nearest numeric MD search matches it to MD 1,000 and attributes the 100 mD plug to class 1. The SandiMin core-fit reader can make the analogous wrong porosity/permeability pairing. Both results are finite and geologically plausible; the correct behavior in the absence of a stored TVD↔MD transform is refusal, while a valid transform would place the plug at class 2.

**Self-refutation attempt.** I confirmed that both readers do filter to the active core set, so this is not an old-delivery leak. I then traced every direct caller looking for a later datum check or survey transform and found none. The datum declaration alone cannot help because the importer deliberately preserves the delivered number. The existence and use of `require_active_core_md` in neighboring depth-pairing readers is direct evidence of the intended refusal boundary; these two readers bypass it. The hard-coded `CORE_MATCH_TOL_M = 1.0` in the same facies path is also raw-project-unit dependent, but the scenario does not rely on that secondary defect because the mismatched numbers are exactly equal.

**Severity: P1.** A supported, explicitly declared non-MD core delivery can silently train or QC against the wrong log interval in normal use.

## P1 — Cutoff sensitivity silently disables an entered permeability cutoff on a well whose PERM curve is entirely missing.

**Decisive code.** The binding rule in `CLAUDE.md:828-829` says a requested permeability cutoff is always active and lack of measured PERM is not an exemption. The deterministic pay summary follows it: `src-tauri/src/workflow.rs:4549-4553` sets `has_perm_cut` from the request alone, and `classify_sample` at `src-tauri/src/workflow.rs:4855-4911` makes a missing PERM sample fail. The sweep engine diverges at `src-tauri/src/workflow.rs:4935-4960`: it activates the same cutoff only if `perm.iter().any(finite)`. `src/ui/cutoffDialog.ts:519-550` sends any finite held PERM entry to the sweep; it does not block or clear it when the selected well lacks PERM.

**Concrete failure scenario.** Use a 10 m zone whose VSH = 0.10, PHIE = 0.20, and SWE = 0.30 throughout, with no finite PERM samples. Enter a held `PERM ≥ 10 mD` cutoff and sweep VSH over a range that includes permissive values. The deterministic pay summary correctly books 0 m net and sets its “PERM cutoff, no data” evidence flag. In `compute_sweep`, `has_perm_cut` becomes false, so the same samples pass and the permissive end of the sweep reports 10 m net and NTG = 1.0. The two screens now give opposite pay answers for identical held cutoffs.

**Self-refutation attempt.** I checked whether the UI disables the run, omits the PERM request, or post-filters the returned series. It does none of those; its status logic can even describe the well as having pay because the peak is positive. I checked the sweep tests at `src-tauri/src/workflow.rs:11860-11958`; they exercise `perm_min = None`, so they do not pin the missing-PERM case. The nearby comment claiming agreement with `run_pay_summary` is contradicted by the latter's explicit request-only activation rule.

**Severity: P1.** This is a normal sensitivity workflow that returns a finite, optimistic pay curve after silently dropping a cutoff the user explicitly entered.

## P2 — Results-QC returns unbounded per-depth arrays as JSON instead of the required byte-packed IPC payload.

**Decisive code.** The binding IPC rule in `CLAUDE.md:16-18` requires numerical arrays to cross Tauri as bytes, not raw JSON. `src-tauri/src/resultsqc.rs:64-88` derives `Serialize` for a result containing raw `Vec<f32>` depth, every method series, and `sw_min`, `sw_max`, and `spread`. `src-tauri/src/resultsqc.rs:365-449` accepts optional depth limits, fetches the full frame, and applies no sample cap or decimation. `src-tauri/src/lib.rs:3901-3911` returns that struct directly, while `src/ipc.ts:2931-2955` expects JavaScript number/null arrays rather than a byte buffer.

**Concrete failure scenario.** Request whole-well Results-QC (both optional depth limits null) on a 500,000-sample high-resolution well with inputs for all seven implemented models. The response contains 11 full-length numeric arrays: depth, seven method arrays, and min/max/spread—5.5 million JSON scalar elements. The equivalent Float32 payload is about 22 MB before framing; decimal JSON, nested arrays, strings, parsing, and duplicate JS allocations make it substantially larger and force a long serialization/parse pause or an out-of-memory/frozen panel on an otherwise valid well. There is no backend limit to turn that into a bounded request.

**Self-refutation attempt.** I checked the current caller: the panel often supplies zone bounds, which reduces many routine requests. It also supports whole-well scope and sends null bounds, and the backend contract itself is deliberately not caller-dependent. Unlike byte-packed curve-frame/track paths elsewhere in `equations.rs`, Results-QC has no packing layer. This does not prove every well will freeze, so I have not classified it as wrong petrophysical math; it is a concrete scale-triggered contract failure.

**Severity: P2.** The violation is reachable and can make a valid analysis fail at scale, but it does not itself change a computed petrophysical value.
